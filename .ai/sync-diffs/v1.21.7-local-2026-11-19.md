### B04. 强制邀请的 OAuth 两阶段注册

代码：[登录换 token](../../internal/logic/auth/oauth/oAuthLoginGetTokenLogic.go)、[完成注册](../../internal/logic/auth/oauth/oAuthRegisterLogic.go)、[临时身份缓存](../../internal/logic/auth/oauth/oauth_pending.go)、[handler](../../internal/handler/auth/oauth/oAuthRegisterHandler.go)、[路由](../../internal/handler/routes.go)、[类型](../../internal/types/types.go)、[缓存 key](../../internal/config/cacheKey.go)。

| 请求 / 响应 | 当前契约 |
| --- | --- |
| `POST /v1/auth/oauth/login` | 发起授权；`OAthLoginRequest` 仍是 `method/redirect` |
| `POST /v1/auth/oauth/login/token` | `method`、`callback`，新增可选 `invite` |
| 新身份、强制邀请、未给邀请码 | 返回成功 envelope，data 中 `invite_required: true`、`oauth_token`；`token` 为空，不是登录成功 |
| `POST /v1/auth/oauth/register` | 新增路由，提交必填的 `oauth_token`、`invite` |
| 完成注册 | 验证并创建/找到用户，签发 `token`，记录登录状态 |

必须保留的顺序与边界：

1. Google/GitHub/Facebook/Apple/Telegram 仍先由服务端验证提供方身份；前端不得凭自报 OpenID 建号。
2. 已存在的身份直接走登录路径，不因强制邀请而要求老用户重新注册。
3. 新用户有邀请码时先查邀请人；无邀请码且开启强制邀请时，将已验证身份缓存到 Redis `auth:oauth_pending_register:<ticket>`，TTL 10 分钟；**此时不写 user/身份/钱包记录、不签发登录 token**。
4. 第二步仅提交 ticket + 邀请码，不重放已消费的提供方回调；失效 ticket 返回 InvalidAccess，错误邀请码可以重试。有效新账号保存 `RefererId`。
5. 账号和 token 成功后删除 ticket；当前实现为 `GET → 注册/签 token → DEL`，删除错误被忽略，**不能宣称已由原子 GETDEL/锁证明并发下严格单次消费**。并发/Redis 删除失败等是待验证边界，不在本次文档任务中改实现。
6. `cf_token/captcha_id/captcha_code/slider_token` 尚未加入上述 OAuth 请求结构，不能沿用旧前端台账把“邀请字段落地”扩大成“所有验证码字段已由后端验证”。

前后端应成对交付：前端识别 invite-required 分支、保持待注册状态并提交第二阶段；若只部署后端，旧客户端会误把空 token 当成授权结束。生成契约应基于本地后端，不是浮动上游 Swagger。
