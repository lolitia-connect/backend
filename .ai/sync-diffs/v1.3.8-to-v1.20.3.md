## Summary

Major architectural divergence between upstream and local fork. Upstream uses GORM with its module layout; the fork uses entgo with hand-written golang-migrate DDL. Direct merge attempted but produced 2536 conflicts and was aborted.

**Recommendation**: Manual feature-by-feature porting using the prompts in `.ai/prompts/`.

**Where this sync landed**: every feature that is a self-contained behaviour or schema change has been ported, with tests, and `go test ./...` passes (the sole exception is the pre-existing `pkg/tool TestRedisPing`, which needs a local Redis on `[::1]:6379`). What remains is deliberately listed as blocked or not-applicable rather than silently skipped — see each entry's **Why not**, and the **Architecture Updates That Are Upstream-Only** section for the commits that are layout, not behaviour.

### 1. Wallet Table Extraction
- **Commits**: `c084c0a0`, `3cda1222`, `a5a5d745`, `a0891426`, `ae7b8d76`
- **Impact**: Breaking change - drops `user.balance/gift_amount/commission` columns
- **Local Action Needed**:
  - Create `ent/schema/user_wallet.go`
  - Write data migration: `initialize/migrate/database/mysql/0XXXX_migrate_user_balance_to_wallet.sql`
  - Update all balance-related logic to use UserWallet
- **Status**: ✅ Completed (2026-10-05) — all five stages landed as one reviewed change
- **Implementation**:
  - `ent/schema/user_wallet.go` + regenerated ent (`ent/userwallet*`); `balance`, `gift_amount` and `commission` removed from `ent/schema/user.go`
  - `internal/model/wallet/{model.go,default.go}` — `Wallet` entity, `Available()`, `Reserve(amount) (gift, remainder)`, and the `Model` interface (`FindOne`, `FindByUserIds`, `Insert`, `UpdateBalanceFields`, `UpdateCommission`), exposed as `Store.Wallet()`. Accounts are only ever soft-deleted, so there is no delete method
  - `internal/model/user` — money fields, mappings and `SetBalance`/`SetCommission`/`SetGiftAmount` mutations removed from the user entity
  - Logic rewired: `purchaseLogic`, `renewalLogic`, `resetTrafficLogic`, `preCreateOrderLogic`, `closeOrderLogic`, `unsubscribeLogic`, `commissionWithdrawLogic`, `queue/logic/task/quotaLogic`, `queue/logic/order/activateOrderLogic` (commission credit and recharge), `portal/purchaseCheckoutLogic` (balance payment), plus the admin create/basic-info edits
  - Display projections (`currentUser`, `getUserDetail`, `getUserList`, `queryUserInfo`) hydrate the retained `types.User` money fields from the wallet, so the API shape is unchanged for the frontend
  - Migrations `02158_user_wallet.{up,down}.sql` (create + backfill) and `02159_drop_user_money_columns.{up,down}.sql` (drop + restore-from-wallet), both engines
  - Tests: `internal/model/wallet/model_test.go` (gift-first split, exact cover, exhaustion, zero/negative amount, no-gift, overdraw guard)
- **Why it is adapted rather than copied**:
  - **Surrogate primary key.** Upstream makes `user_id` the primary key of `user_wallet`; every schema in this fork uses a surrogate `id`, so `user_wallet` follows that convention and one-wallet-per-user is enforced by `UNIQUE (user_id)` / `uni_user_wallet_user_id` instead. Same contract, idiomatic to the local ent layout
  - **No `SELECT … FOR UPDATE`.** Upstream's `FindOneForUpdate` locks the row before deciding how much money moves. The fork's generated ent is built from a stripped template that contains **no `Modify(func(s *sql.Selector))` and no `OnConflict`** on any of the 38 entities, so a row lock cannot be expressed through the builders. The replacement keeps the reservation *inside* the same transaction as the order insert and re-reads the wallet there, so a concurrent order cannot spend the same credit twice; the residual race is a lost update on a row that was already re-read, not a double spend
  - **Self-healing first write.** `UpdateBalanceFields`/`UpdateCommission` insert the row when it does not exist yet and fall back to an update if a concurrent writer won the insert race (`ent.IsConstraintError`). Upstream seeds on first `FindOneForUpdate`; this fork seeds on first write so that no account-creation path (password, phone, device, OAuth, admin) has to remember to open a wallet, and the read-only display paths stay read-only
  - **`types.User` keeps its money fields.** They are no longer stored on the user entity but are still part of `types.User` in `internal/types/types.go`, so the admin console and client API keep working without a response-shape break; the display logics fill them from the wallet

### 9. V2 Checkout Events
- **Commits**: `7f670b28` (V2 checkout events + session flow), `6ed7775f` (idempotent checkout retries)
- **Impact**: A pollable/streamable checkout surface on top of the existing order creators, plus a durable transactional outbox for order state changes
- **Status**: ✅ Completed (backend) — one deliberate omission, see below
- **Implementation**:

  **Outbox and schema**
  - `ent/schema/order_event.go` (new entity, table `order_event`) and four `order` columns: `state_version`, `idempotency_key`, `idempotency_hash`, `guest_checkout_token_hash`
  - Migration `02160_order_events_and_idempotency` (mysql + postgres) creates the table and adds the columns, with `idx_order_idempotency_key` unique so a replayed key collides instead of silently duplicating an order, and `idx_order_event_{order_id,published_at}_id` for replay and publishing
  - **Deviation**: upstream migration number is `02140`; the fork already used `02160`, so the same content landed there
  - **Deviation**: upstream stores the guest credentials on the order (`guest_auth_type`, `guest_identifier`, `guest_password_hash`, `guest_invite_code`, migration `02138`). The fork already keeps them in the `temp_order:<order_no>` Redis record, so only `guest_checkout_token_hash` was added. Consequence: a replayed idempotent create cannot compare the guest identity after that record expires, and is refused instead of served (`guestIdentityMatches` in `v2OrderLogic.go`)

  **Versioned transitions (the fork's ent equivalent of upstream's GORM transitions)**
  - `internal/model/order/event.go` (new): status/event-type constants, `EventTypeForStatus`, `PaymentStatus`, `FulfillmentStatus` (the single source of truth for the client-visible `payment_status`/`fulfillment_status` strings, used by both the outbox payload and the V2 snapshot), the `Event` row, `EventPayload`, `NewEventFor`, `ParseEventPayload`, and the `EventModel` interface
  - `internal/model/order/event_default.go` (new): the ent-backed `EventModel`. `MarkPublished` is conditional on `published_at IS NULL`, so two publishers cannot both count one row
  - `internal/model/order/transition.go` (new): `UpdateOrderStatus` (keeps the fork's permissive "a late payment still completes a closed order" semantics, but publishes an event only when the status actually moved, so a callback retry cannot emit a second `order.payment_paid`) and `FinishOrder` (conditional `paid → finished`, emits `order.fulfilled`)
  - `defaultOrderModel.Insert` writes `state_version = 1` and the `order.created` event in the same call; `orderUpdate` deliberately does **not** write `state_version`, and `Update` rejects a direct status change — the counter can only move through `transition.go`
  - `repository.Store` gained `OrderEvent()`

  **Delivery**
  - `internal/orderstream` (new): the Redis pub/sub channel naming, `order-events:<order_no>`
  - `queue/logic/order/publishOrderEventsLogic.go` (new, `@every 5s`): publishes unpublished events and marks them; stops at the first Redis failure so the backlog is retried in order
  - `queue/logic/order/cleanupOrderEventsLogic.go` (new, daily): drops published events past the 30-day replay window
  - `queue/logic/order/activateOrderLogic.go` now calls `FinishOrder` instead of writing the status directly, so activation is versioned and announced

  **V2 HTTP surface**
  - `internal/orderflow` (new): the context-carried idempotency metadata (`WithIdempotency`/`ApplyIdempotency`/`GuestCheckoutToken`). All five creators (`order/purchaseLogic`, `order/renewalLogic`, `order/resetTrafficLogic`, `order/rechargeLogic`, `portal/purchaseLogic`) call `ApplyIdempotency`, which is a no-op for V1
  - `internal/logic/public/order/v2OrderLogic.go` (new): `createOrder` dispatches to the existing creators, then `CreateAndCheckout`/`Checkout`/`GetOrder`/`EventTicket`/`Session` add authorization, the snapshot, the SSE ticket and the checkout response
  - `internal/handler/public/order/v2OrderHandler.go` (new): five JSON handlers plus the SSE handler (`sse.NewWriter`, replay from the event table, 20s heartbeat, 5s catch-up, ticket expiry sentinel, per-ticket connection cap)
  - `internal/handler/v2_order_routes.go` (new), called from `internal/transport/httpserver/server.go`: `/v2/public/orders` with `OptionalAuthMiddleware` + `DeviceMiddleware`, and a second group for `/:orderNo/events` **without** `DeviceMiddleware` (EventSource cannot participate in the native-device response encryption protocol)
  - **Deviation**: upstream's `CheckoutDependencies`/`newCheckoutLogic()` does not exist here; `checkoutResponse` calls `portal.NewPurchaseCheckoutLogic(l.ctx, l.svcCtx)` directly
  - **Deviation**: upstream `dto.*` → the fork's `internal/types` (+ `apis/types.api`, `apis/public/portal.api`), including the new `V2*` types
  - **Deviation**: upstream's `V2OrderPayment.Stripe` is omitted. `apis/types.api` declares `StripePayment`, but the generated `internal/types/types.go` has no such type and `purchaseCheckoutLogic` always returns a `checkout_url`, so there is nothing to populate
  - **Deviation**: upstream returns a checkout capability on the response of `PurchaseCheckout` after validating `dto.CheckoutOrderRequest.CheckoutToken`. The fork's checkout logic is not part of this sync (see the omission note below), so the V2 logic authorizes the caller **before** delegating and does not forward the token

  **V1 portal hardening carried by the same commit (in scope, and it changes the V1 contract)**
  - `portal/purchaseLogic.go` now issues a guest checkout capability, persists only its SHA-256 (`constant.CheckoutTokenHash`), stores the token in `temp_order:<order_no>`, and returns it in `PortalPurchaseResponse.CheckoutToken`
  - `portal/queryPurchaseOrderLogic.go` gained `authorizePurchaseOrder`, which accepts either the authenticated owner or the capability, and `validateUserAndEmail` was **deleted** — upstream's reasoning is that an identifier is not authentication and must never be used to mint a session.   - `IssuePurchaseSession` was extracted so the V1 status endpoint and the V2 session exchange cannot drift
  - `middleware.OptionalAuthMiddleware` (new) attaches the user when a valid session is present and otherwise continues anonymously; an invalid token is treated as anonymous because the capability check is what authorizes the request

  - Consequence: a retried checkout re-creates a payment session at the provider rather than reusing the first `trade_no`. Revisit only if the payment-currency snapshot is ever ported

  **Landed from `6ed7775f`**
  - `closeOrderLogic.go` restores plan inventory only for a new subscription purchase (`order.TypeSubscribe`). Renewals and traffic resets reference a plan without consuming its stock, so closing one used to inflate stock that was never reserved. The rule is a named helper, `reservesPlanInventory`, with a table test over all four order types
  - `internal/model/order/order.go` gained the `TypeSubscribe`/`TypeRenewal`/`TypeResetTraffic`/`TypeRecharge` constants for the values the creators already wrote as literals

  **Tests**: `internal/model/order/event_test.go`, `internal/orderstream/channel_test.go`, `queue/logic/order/orderEventsLogic_test.go` (miniredis-backed publisher/cleanup), `internal/logic/public/order/v2OrderLogic_test.go`, `internal/logic/public/order/closeOrderLogic_test.go`, `internal/handler/public/order/v2OrderHandler_test.go`

## Architecture Updates That Are Upstream-Only

These commits in `v1.3.8..v1.20.3` change how upstream is *built*, not what it *does*. They are recorded here so that a later sync does not rediscover them as "missing features". None of them is portable without first adopting upstream's layout, and the local fork deliberately keeps entgo and the flat logic tree.

| Commit | What upstream did | Why it does not apply here |
| --- | --- | --- |
| `c9be2ce8` | Split the `entity` package into per-domain packages | The fork never had a shared `entity` package; `internal/model/<domain>` already owns its own types. Nothing to split |
| `df9a5a47` | Freeze per-module configuration at module construction | Depends on upstream's `internal/module/*` constructors. The fork wires dependencies through the single `svc.ServiceContext`, whose config is already loaded once at boot |
| `27` (the bulk series) | Module absorption, repository ownership, per-domain transactions | Pure movement of GORM code between `internal/module/*` packages. The fork is a flat `internal/logic/*` tree on ent with hand-written SQL migrations |
| `protocol_normalize.go` + `valid*` helpers | A protocol **normalization layer** that every node read/write routes through | 1009 lines, stdlib-only imports, so the file travels — but it references ~20 `Protocol` fields that exist only upstream (`Plugin`/`PluginOptions`, `Version`/`Mode`/`Network`, `SSRProtocol`/`ProtocolParam`/`ObfsParam`, `ALPN`, `CertPinSHA256`, `Heartbeat`, `QUICCongestionControl`, `TrafficPattern`, `UserHintIsMandatory`, `EchEnable`, `EchServerName`, `CertDNSProvider`, `CertDNSEnv`). It was initially assumed to block #16 and #17 as well; both turned out to be independently portable and were landed. The part of it that needs none of those fields was ported as #35 |

The architecture-shaped changes that *did* land are the wallet extraction (#1), the edge manifest (#16) and the protobuf transport (#17). For #1, upstream's endgame was a module-boundary split, but its observable contract — money moves on a billing-owned table, not the identity row — is expressible on ent, so the behaviour was ported and the boundary adapted to local conventions. For #16 and #17, the shared "protocol model" that made them look blocked was only a read surface: the manifest projects `node.Protocol` without writing to it, and the protobuf messages describe exactly the flat shape `types.Protocol` already has.

### 36. Self-Signed Certificate Pinning (`63e33754`, `e73cc438`)
- **Impact**: `AllowInsecure` on a self-signed `cert_mode` used to be all-or-nothing — the panel could only tell a node to skip certificate verification entirely, with no way to verify against a known fingerprint
- **Status**: ✅ Completed (backend, 2026-10-05) — panel side landed; **node side still outstanding** (handed off, see below)
- **Implementation**:
  - [internal/model/node/cert_pin.go](backend/internal/model/node/cert_pin.go) — `NormalizeCertPinSHA256` (trim, lowercase, exactly 64 hex characters), `CarryForwardCertPin`, and `(*Server).ApplyReportedCertPin(protocolType, fingerprint) (bool, error)`
  - `Protocol.CertPinSHA256` (JSON `cert_pin_sha256`, omitempty) added to `internal/model/node/server.go`, `internal/types/types.go` and `apis/types.api`
  - The panel reads `X-Node-Certificate-SHA256` in [serverPushStatusHandler.go](backend/internal/handler/server/serverPushStatusHandler.go) (`certificateSHA256Header` in [helpers.go](backend/internal/handler/server/helpers.go)) and stores the value from [serverPushStatusLogic.go](backend/internal/logic/server/serverPushStatusLogic.go)
  - `normalizeProtocolNoopFields` canonicalises the pin and clears it when `cert_mode != "self"`; `clearCertificate` clears it too, so a pin can never outlive the certificate it describes
  - [adapter/adapter.go](backend/adapter/adapter.go) — `allowInsecure := protocol.AllowInsecure && protocol.CertPinSHA256 == ""`, i.e. **a pin forces verification** (`e73cc438`'s AllowInsecure clearing, expressed as a derivation instead of a mutation so the stored value is not destroyed)
  - Tests: `cert_pin_test.go` (7 functions) and `TestAdapterProxyCertPinForcesCertVerification` in `adapter/utils_test.go`
- **Why it is adapted rather than copied**:
  - **Column-scoped write instead of a full-row save.** Upstream records the pin inside the same heartbeat that saves the whole server row. This fork's generated ent is built from a stripped template with no `Modify`/`OnConflict`, so a full-row heartbeat save is exactly the lost-update hazard the fork avoids elsewhere; `ApplyReportedCertPin` writes the single `protocols` column with `UpdateOneID(...).SetNillableProtocols(...)`
  - **Cache invalidation is conditional.** The store method returns a `changed` flag, and the logic invalidates the node config cache only when the pin actually moved. Upstream invalidates unconditionally on report; with a 64-hex value that is stable in the steady state, that would mean a full config re-distribution on every heartbeat
  - **`CarryForwardCertPin` has no upstream equivalent.** Upstream's admin update merges into the stored row; this fork's `updateServerLogic` rebuilds the entire protocol list from the DTO, which has no pin field — so a node-reported pin would be wiped by any admin save. `CarryForwardCertPin` matches by `type` **and** `id` (per the `type:id` identity rule) and only for `cert_mode: self`
- **Node-side handoff**: `node-backend/.ai/panel-sync-notes.md` §9 — the node must send `X-Node-Certificate-SHA256` on every request and must treat a non-empty `cert_pin_sha256` as "verify, do not fall back to insecure"

### #9 — guest checkout polling now needs the capability (breaking for the V1 portal flow)

`GET /v1/public/portal/order/status` no longer accepts `auth_type` + `identifier` as proof of
ownership. An identifier is not authentication: with a paid guest order it let anyone who knew the
buyer's email mint a session token for that account (`validateUserAndEmail` was deleted for exactly
this reason). The endpoint now requires the `checkout_token` returned by
`POST /v1/public/portal/purchase`:

- `POST /v1/public/portal/purchase` response gained `checkout_token` (string, present only for guest
  purchases). The client must keep it — it is returned exactly once and only its hash is stored.
- `GET /v1/public/portal/order/status` gained a required-for-guests `checkout_token` query
  parameter. A signed-in user polling their own order does not need it.
- The session token that comes back is unchanged, so only the "which values do we send" step changes.
- Any order created before this change has no stored hash; the backend falls back to the
  `temp_order:<order_no>` Redis record for those, so an in-flight checkout still completes.

The same capability is what the V2 surface uses, so a frontend that adopts `checkout_token` here is
already compatible with `/v2/public/orders`.
